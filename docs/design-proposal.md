# TopoGo：19×19 拓扑围棋本地双人游戏开发提案

版本：v1.0 proposal；整理日期：2026-10-02。

## 0. 项目目标与已作出的产品决定

开发一个中文界面的本地网页游戏。两个人在同一台电脑、同一个浏览器窗口中轮流执黑白，默认棋盘有 361 个独立落点。必须支持普通平面棋盘、环面 T²、莫比乌斯带和实射影平面 RP²；克莱因瓶一并实现，作为相近模型的对照。

这里的“射影空间”具体取二维实射影平面，不是高维 RPⁿ。“本地双人”首先指同机轮流操作，不指局域网两台设备联机。第一版不需要账号、在线匹配、后端数据库、云端 AI API 或神经网络训练。

最终交付必须同时包含：完整合法对弈、拓扑邻接可视化、对局保存恢复、终局协商和确定性算分、中盘辅助评估。不能只交付一个能摆棋子的 3D 演示。

必须区分三种输出：

- **规则事实**：当前棋串、气、合法着法、实际提子、超级劫等，可以确定计算。
- **终局结算**：双方确认死子之后，按本提案规则精确计算胜负；尚有死活争议时允许恢复对弈。
- **中盘预测**：势力、薄弱棋串、参考估值，仅为启发式/有限搜索，不冒充确定胜负或专业胜率。

本文件中的数值参数、软件栈和开发阶段都是本项目的设计决定，不代表某种公认的“拓扑围棋官方规则”。

## 1. 已检索的相关项目

### 1.1 3dgo：最可能对应记忆的旧项目

作者于 2017 年在 OGS 论坛发布的项目介绍，标题为 “3dgo - new web app for playing Go on any topology”。原帖有环面、其他网格的截图，并在回复中说明加入了克莱因瓶。两次停着后进入双方确认领地的阶段。[R1]

本次找到了原始介绍，但**没有确认该项目仍有可用部署，也没有确认对应围棋源码仓库**。不要把 GitHub 上 `erikvanzijst/3dgo` 误认成这个项目；它是 Go 语言的线框渲染器。

### 1.2 goplayerjuggler/goVariants

MIT 许可，ECMAScript 实现，包含普通棋盘和环面棋盘的落子、气、提子及计分。其 README 明确写明 **ko 与 superko 尚未实现**。可以参考，不应当未经补全就作为完整裁判。[R2]

### 1.3 govariantsteam/govariants

Go variants 平台，AGPL-3.0。README 将规则和棋盘显示拆开；完整站点包含客户端、服务端和数据库，另外提供无需数据库的 variant demo 开发路径。适合参考插件化结构；当前同机双人版本不必照搬整个服务器。[R3]

### 1.4 bernds/q5Go

GPL-2.0。已有环面棋盘、重复显示周边棋盘区域和拖动视图等交互；README 明确指出环面棋谱需要非标准 SGF 表达。适合作为环面展开视图与复盘操作的参考。[R4]

### 1.5 lightvector/goscorer

MIT 许可，有 Python 和 JavaScript 版本，包含日式风格计地、双活相关处理及面积计分实现。README 明确要求死子已正确标记，并不保证任意奇异局面；它不是一个自动解决全部死活的引擎，也不能未经拓扑改造直接用在本项目。[R5]

**建议：独立编写一个小型 TypeScript 图围棋内核，参考以上项目。记录实际引用的代码与许可证，不把许可证标签不同的代码直接混入新项目后统一改标。**

## 2. 数学模型：先固定图，再做显示

### 2.1 独立落点与坐标

令 N=19，顶点集合为

`V = {(x,y): 0 <= x,y < N}`，`id(x,y) = y*N+x`。

程序坐标 x 向右、y 向下。棋谱和历史使用不可变的 canonical vertexId。界面可显示 A–T（跳过 I）与 19–1，但显示坐标不能替代内部 ID。

“19×19”在本提案中意味着 **361 个独立落点**。采用切口在落点之外的邻接模型：落点可理解为基本方形的 N×N 个小格中心；把相邻中心连接起来，画成常见的 19×19 棋盘。边缘之外的连接表达粘合。

不能将第一列与最后一列的落点直接合并，否则会减少独立落点数量。不能把所有 (x,y) 与 (N-1-x,N-1-y) 合并；RP² 所要求的是基本区域边界粘合，不是整个方形内部两两合并。

### 2.2 统一的跨边邻接约定

内部四方向邻点存在时，均按普通矩形网格处理。只在越界时应用下表。所有坐标变换中的翻转都是 `N-1-coordinate`。

| topologyId | 向左越界 | 向右越界 | 向上越界 | 向下越界 |
|---|---|---|---|---|
| plane | 无 | 无 | 无 | 无 |
| torus | (N-1,y) | (0,y) | (x,N-1) | (x,0) |
| mobius | (N-1,N-1-y) | (0,N-1-y) | 无 | 无 |
| klein | (N-1,N-1-y) | (0,N-1-y) | (x,N-1) | (x,0) |
| projective | (N-1,N-1-y) | (0,N-1-y) | (N-1-x,N-1) | (N-1-x,0) |

这里采用：环面零组反向，克莱因瓶一组反向，RP² 两组反向。基本方形两组对边反向识别得到 RP² 的数学依据见 [R6]、[R7]。

`neighbors(v)` 必须返回去重的 vertexId 集合，无自环、无重复邻点，且满足无向性：u 是 v 的邻点当且仅当 v 是 u 的邻点。用于画接缝的有向记录可以保留不同出边方向，但规则层必须去重。

### 2.3 RP² 的角点是重点验收项

N=19 时，`(0,0)` 向左与向上均到达 `(18,18)`。所以：

`neighbors(0,0) = {(1,0), (0,1), (18,18)}`。

其余三个角同样有三个不同邻点。四角以外的 357 个点均有四个不同邻点。两条不同的跨缝路径通向同一个空点，只能提供一口气。

这不是把射影平面误做成“有边界”：这个曲面仍是闭曲面。这里改变的是离散棋盘在四个点的局部度数。四价、全四边形的闭曲面胞腔分解满足 E=2V、F=V，因而 χ=0；RP² 的 χ=1，因此不能同时强求这种模型处处四价、所有面四边形。

### 2.4 显式面数据与曲面验证

游戏规则只需要图 G=(V,E)，但为了确保所声明的曲面真正正确，本项目同时生成四边形面列表 F，而不是只在配置中手填 Euler 数。用 K=(V,E,F) 验证嵌入。裸图本身不能唯一确定曲面或环路同调。

记 `v(x,y)=id(x,y)`。面生成方式如下：

1. 内部面，0<=x,y<N-1：
   `[v(x,y), v(x+1,y), v(x+1,y+1), v(x,y+1)]`。
2. 左右周期接缝的面，0<=y<N-1：
   `[v(N-1,y), v(0,y), v(0,y+1), v(N-1,y+1)]`。
3. 左右翻转接缝的面，0<=y<N-1：
   `[v(N-1,y), v(0,N-1-y), v(0,N-2-y), v(N-1,y+1)]`。
4. 上下周期接缝的面，0<=x<N-1：
   `[v(x,N-1), v(x,0), v(x+1,0), v(x+1,N-1)]`。
5. 上下翻转接缝的面，0<=x<N-1：
   `[v(x,N-1), v(N-1-x,0), v(N-2-x,0), v(x+1,N-1)]`。
6. 环面额外角面：
   `[v(N-1,N-1),v(0,N-1),v(0,0),v(N-1,0)]`。
7. 克莱因瓶额外角面：
   `[v(N-1,N-1),v(0,0),v(0,N-1),v(N-1,0)]`。
8. RP² 不额外添加角面。两对重复接缝边在规则图中合并；上述列表已给出所需 360 个四边形面。

只为该 topology 所启用的接缝生成相应面。面列表中的顶点顺序是局部边界顺序；非可定向曲面不能要求所有面存在一致全局定向。

本提案提供的 Python 参考脚本已对 N=5、9、13、19 的五类棋盘运行以下检查：每条边的面关联数、每个顶点 link 是单圈或单路径、可定向性、边界分支、顶点度数和 Euler 数。N=19 输出为：

| 棋盘 | V | E | F | χ | 可定向 | 边界分支 | 不同邻点度数 |
|---|---:|---:|---:|---:|---|---:|---|
| plane | 361 | 684 | 324 | 1 | 是 | 1 | 4 个度2；68 个度3；289 个度4 |
| torus | 361 | 722 | 361 | 0 | 是 | 0 | 361 个度4 |
| mobius | 361 | 703 | 342 | 0 | 否 | 1 | 38 个度3；323 个度4 |
| klein | 361 | 722 | 361 | 0 | 否 | 0 | 361 个度4 |
| projective | 361 | 720 | 360 | 1 | 否 | 0 | 4 个度3；357 个度4 |

这些计数是本提案指定的离散模型的计算结果，不是任意离散化都相同的顶点/边/面数。验收时必须由实现真正计算得到，不得硬编码通过测试。

## 3. 规则合同：TopoGo Area v1

### 3.1 固定规则

采用基于图连通性的面积计分，参考 Tromp–Taylor 对提子、重复局面和面积的简洁定义，但明确修改为禁止自杀，并加入适合同机玩家的终局协商流程。[R8]

- 黑先白后；不设让子；默认白贴 7.5 分，可在新建游戏时修改。
- 7.5 是原型默认参数，不宣称对任何拓扑均公平。开局后贴目和拓扑不可修改。
- 每步落在空顶点；先提掉无气的对方棋串，再检查自己的棋串是否有气。
- 禁止自杀；不能因落子位置起初被包围就直接禁止能提子的着法。
- 启用 positional superko（PSK）：一次实际落子后的完整棋子分布不得与当前有效对局历史中的任何局面相同，包括初始空棋盘。
- 停着永远不因 PSK 被禁止；仍记录停着和轮次。无 pass-stone 额外分数。
- 两次连续停着进入终局协商，不直接宣告胜负。
- 认输需要确认，随后立即按认输结局结束。

### 3.2 棋串和气

同色石子在图上的最大连通分量为一个棋串 C。

`liberties(C) = {v: board[v]=EMPTY and some u in C has v in neighbors(u)}`。

棋串和气一律使用集合，气数不是“相邻空方向数量”。跨缝相连的棋串必须作为一个棋串处理。

### 3.3 applyMove 的事务顺序

拒绝非法阶段、越界或已占位置后，在副本上试下。收集相邻的不同对方棋串，找出落子后为零气的串，统一提走；随后重算己方新串的气。若为零，则整步撤销。若棋盘序列化键与有效历史重复，也整步撤销。通过后才提交棋盘、提子记录、轮次、历史、手数和 lastMove，并把连续停着计数归零。

非法操作不得改变任何状态，也不得把连续停着计数归零。

### 3.4 历史与 PSK

第一版建议直接采用固定 vertexId 顺序下的 361 位颜色序列作为棋盘键；无需为了性能急着使用概率哈希。键的命名空间可包含 topologyVersion 和 N。PSK 比较只依赖该局棋盘的石子颜色分布，不将 toPlay 加入键，否则变成 SSK。

不要把旋转、平移、镜像或图自同构归一化后的局面作为 PSK 键：不同实际落点的局面并不因为对称而相同。拖动环面视图只改变显示映射，不改变真实棋盘或其键。

悔棋后，应从当前有效历史前缀重建键集合；不能让被撤销的未来局面继续阻止落子。停着会出现重复棋盘键，因此采用增减计数时要使用 Map<key,count>，不能错误删除仍出现在更早历史中的键。361 点原型可直接由历史重建，优先保证正确。

### 3.5 游戏状态机

`setup -> playing -> scoring -> finished`。

两次连续停着：playing -> scoring。进入 scoring 时保留未移除死子的真实棋盘快照和 nextToPlay。

在 scoring 中，玩家点击一颗棋子，切换该完整棋串的 proposedDead 标记；这只修改预览，不改真实行棋历史。黑白分别确认同一个 proposal revision；任意标记变化都清除两人的确认。两人确认相同版本后完成计分并进入 finished。

任何一方可选择恢复对弈：清除死子标记与确认，恢复两次停着后的原棋盘，保留历史，沿用其 nextToPlay（即第一次停着的玩家），把 consecutivePasses 设为 0。不得把预览中移除的死子永久留在棋盘外。

未就死活达成一致时不允许以当前估值强行判胜。双方可继续实际提掉争议棋，或重新同意终局方案。局域网身份认证不属于本版范围，同机界面以“黑方确认”“白方确认”明确操作语义。

## 4. 终局面积计分：确定性裁判

双方确认的死子集合为 D。复制真实棋盘，将 D 中的石子移除。保留下来的黑、白石子分别数为 B、W。对剩余空点按实际邻接做 flood fill。

对每个空连通分量 R，收集紧邻它的石子颜色集合 colors(R)：

- `{BLACK}`：|R| 加入黑方空地 TB。
- `{WHITE}`：|R| 加入白方空地 TW。
- `{BLACK,WHITE}` 或空集：|R| 加入中立空点 U。

最终：`SB=B+TB`，`SW=W+TW+komi`，`margin=SB-SW`。正值黑胜，负值白胜，零为和棋。界面写“黑胜/白胜 X 分”，并列出石子数、空地、贴目和中立空点，避免与中国数子中“子”的换算混淆。

提子计数仅用于过程展示，不再额外加分。双方确认移除的死子也不能再当俘虏重复加分。

每次算分断言 `B+W+TB+TW+U = N*N`。所有值按唯一 vertexId 统计，显示副本、接缝路径和 3D 双面渲染均不重复计数。

双活不能被自动删除。混合颜色边界的公共气为中立；采用本规则时单色边界的私有空点依算法计入面积，不套用日式“整块双活不计地”的额外例外。

**拓扑原则：计分判断空点的图连通分量，不凭 2D 图上是否画出了闭合圈。** 环面上绕一圈的棋串未必围出一个分离区域；这一点必须通过测试例子体现。

## 5. 局势判断：第一版提供什么

### 5.1 始终可算的局部信息

悬停/点击棋串显示石子数、气数和全部气的位置，跨缝高亮；对一气棋串标记“叫吃”，二气棋串显示“二气警示”，但不能把二气直接解释为必死。可列出当前合法的一手提子点以及相应提子数，不能把提子数等同于最佳着法。

### 5.2 即时势力图

在全部空点上解离散调和方程：

`h(v)=sum(h(u) for u in neighbors(v))/degree(v)`。

黑棋固定 +1，白棋固定 -1。全空棋盘定义 h=0。仅有一种颜色时解退化为该色占优，此时 UI 必须提示“仅反映影响；开局不能据此判断领地或胜负”。一旦两色均存在，使用确定性迭代或小型线性求解器，展示残差并确保结果有限且在 [-1,1] 内。

默认用迭代法时给出固定初值、容差和最大次数，例如空点从 0 开始，Gauss–Seidel，maxIterations=5000，residualTolerance=1e-5；未收敛时标注“近似未完全收敛”，不伪造收敛。

显示名称必须为“势力图（启发式）”，不是“真实领地”或“胜率图”。它没有充分处理死活、劫争和最佳对抗，不能用于裁定终局。

### 5.3 弱基线参考估值

支持明确标注的静态参考：保留所有实际棋子，并以 h(v) 对空点软分配，

`estimatedMargin = B-W + sum(h(v) over empty v) - komi`。

这一数值的语义是“势力折算差”，不是预言的终局分差，更不是有统计置信度的结果。早盘、仅一色落子和大量弱棋时应弱化该显示，并显示“尚不适合判断领先”。不得凭空给出 ± 置信区间或胜率百分比。

V1 的中盘辅助判断验收以真实拓扑上的势力、弱棋警示、一手提子和明确局限的参考估值为准；专业棋力另行训练和评测，不混入 V1 的承诺。

### 5.4 第二阶段增强：本地 Monte Carlo / MCTS

在 V1 完成后再加 Web Worker 中的有限预算模拟。所有模拟使用同一个规则内核，复制完整 PSK 有效历史，并在探索树分支时回滚各自的历史。模拟不能偷偷用普通平面规则或忽略禁入点。

模拟优先考虑提子、逃叫吃、连接和合理扩张，保留一定随机探索。不得把启发式过滤后的“候选着法”误标为全部合法着法。固定种子与固定模拟数用于回归测试；实时模式可按 1/3/10 秒预算停止。返回样本数、策略版本、种子和完成状态。

模拟终止后可使用“按当前棋盘直接计算面积”的策略估计；未达到两次停着而因步数或时间截断的样本必须单独标记，不与真实终局混为一谈。展示名称为“模拟策略下的参考估计”。不把随机自我对弈获胜比例叫作校准后的真实胜率，也不让模拟结果自动提交死子判定。

Worker 请求要携带 stateRevision；用户落子/悔棋/切换对局后取消旧请求或丢弃旧回复，防止旧评估覆盖新局面。Worker 能避免后台计算直接占住界面线程，使用方式见 [R10]。

### 5.5 不直接套普通 KataGo 权重

普通棋盘与本提案的跨边邻接不是同一个环境。KataGo 的官方架构说明中包括棋盘位置与 off-board 的处理；不能仅在界面上画出环面，就声称普通训练权重能理解新邻接。[R9]

未来可开发拓扑感知引擎、图网络和自我对弈训练，或专门改造现有引擎及其输入/训练环境；这些是增强路线，不是 V1 的运行依赖。

## 6. 界面与交互

### 6.1 默认 2D 展开视图

中央为 19×19 棋盘；右侧显示当前执棋、拓扑、贴目、手数、提子、操作按钮和分析面板。木纹和动画必须轻量，无外部网络资源。星位是显示标记，不增加规则上的特殊性。

必须包含：新建游戏、停一手、认输、悔棋、前进/后退复盘、返回当前局面、导出、导入、势力图开关、显示气开关、显示接缝开关。

复盘模式默认只读。需要从历史节点继续时，使用明确的“从此处继续”操作，并在确认后丢弃 redo 尾部；不静默修改当前正式对局。

新建不同拓扑必须确认放弃/保存当前局，不能在一盘棋中途直接修改邻接关系。

### 6.2 接缝和幽灵显示

用边缘箭头和可点击的邻点高亮解释粘合。环面可显示周边 2–3 行/列的半透明幽灵副本，并支持拖动显示原点。参考 q5Go 的重复区域交互，但独立实现。[R4]

幽灵点必须映射到同一个 vertexId；点击副本等价于点击本体；状态、提子、历史与分数均只存一次。

莫比乌斯带的跨缝副本需要翻转行号，上下是真实边界。RP² 首先使用独立边缘条带和邻点提示，不把环面的 3×3 周期平铺机械复制到 RP²。角点两条接缝到达同一 vertexId 时可画两条路径，但高亮和规则计数均去重。

### 6.3 3D 视图后置

V1 不依赖 3D。后续可给环面和莫比乌斯带加同步的可旋转模型。非可定向曲面的棋子是附着在抽象顶点上的颜色，同一落点不存在“正面一颗、背面另一颗”的双占用。

RP² 可保持展开图或使用带说明的浸入式示意。显示曲面的自交不能产生新的规则邻接；屏幕上贴近或重叠不代表同一点。点击映射必须回到 canonical vertexId。

## 7. 技术方案

建议单一前端项目：TypeScript + React + Vite，2D 棋盘用 SVG，规则核心为与 React/DOM 无关的纯 TypeScript 模块；复杂评估使用 Web Worker。Vite 支持 react-ts 模板并提供本地开发与打包流程。[R11]

测试采用 Vitest 与 Playwright；两者分别用于模块测试和浏览器流程测试。[R12][R13]

不在提案里锁定臆测的未来软件版本。实施时选择彼此兼容的受支持版本，把实际 Node 与依赖版本记录到 README / engines / lockfile 中，提交 package-lock.json。SVG 的 361 个主落点应以实测满足流畅交互为准，不承诺所有机器上的固定帧率。

TopologySpec 至少包含 topologyId、topologyVersion、N、neighbors、seams、faces、预期曲面类型；validator 从实际结构推导度数、χ、边界和可定向性。

GameState 至少包含 board、toPlay、phase、moves、historyCursor、captures、consecutivePasses、lastMove、ruleset、komi、topologyVersion、scoringProposal 与其 revision、confirmations、result、stateRevision。

建议规则 API：`createGame`、`getGroup`、`getLiberties`、`tryPlay`、`pass`、`resign`、`undo`、`redo`、`toggleDeadGroup`、`confirmScore`、`resumePlay`、`scorePosition`。失败用带 errorCode 的判别联合返回，不用异常替代正常非法落子判断。

建议分析 API：`analyze({state, budget, seed, revision}) -> {method, revision, influence, atariGroups, captureMoves, heuristicMargin, warnings, diagnostics}`。结果类型明确区分 heuristic、simulation 与 agreed-final，不用同一个 score 字段混淆含义。

### 本地运行约定

首次安装依赖可能需要网络；完成安装后，对弈、评估、保存恢复不得依赖互联网。资源全部本地打包，使用 localhost 静态/开发服务。不要承诺 Vite 打包结果一定能通过 file:// 双击 HTML 正常运行，模块和 Worker 均以实际本地服务测试为准。

交付命令至少支持：`npm ci`、`npm run dev`、`npm run typecheck`、`npm run test`、`npm run build`、`npm run test:e2e`。附 Windows 的 start-local.bat，启动失败给出错误提示；不静默下载安装全局软件。生产包通过明确的本地静态服务方式启动。发布包与依赖首次安装步骤分开说明。

## 8. 保存、恢复与文件格式

使用带 schemaVersion 的 JSON 格式作为权威棋谱：包含 topologyId/version、N、规则、komi、完整行动序列、historyCursor、终局协商和结果。初始版本不包含任意摆棋；测试夹具的棋盘构造与正式棋谱导入分开。

每次合法动作、悔棋、恢复对弈和终局修改后自动保存。优先 localStorage，捕获容量/访问失败，并保留手动下载。刷新后恢复该有效历史，而不只是恢复棋子颜色。

导入时校验数据类型、版本、棋盘规模、vertexId 范围、最大文件大小和行动数量，并由内核重放落子/停着，重建 PSK。额外的认输或协商元数据也校验阶段合法性。拒绝未知拓扑版本、非法着法或不一致结果；不能相信导入文件自称的黑胜白胜。

SGF 可作为后续兼容扩展，但自定义拓扑属性必须标明非标准，不能省略拓扑信息后让普通 SGF 阅读器误判为平面棋盘。[R4]

## 9. 验收测试

### 9.1 拓扑构造

N=5、9、13、19 均覆盖。检查邻接无向、无自环、去重、图连通、每条面边确实存在、面关联与顶点 link 正确。计算 χ、边界分支和可定向性；N=19 对照第 2.4 节表格。

具体锚点：

- torus：neighbors(0,7) 含 (18,7)。
- mobius：neighbors(0,7) 含 (18,11)，不因左越界连接到 (18,7)。
- mobius：neighbors(5,0) 不含 (5,18)。
- klein：neighbors(5,0) 含 (5,18)，左右仍翻转。
- projective：neighbors(5,0) 含 (13,18)。
- projective：neighbors(0,0) 恰为 {(1,0),(0,1),(18,18)}。

### 9.2 规则单元测试

普通/跨缝棋串、共享气去重、多串同时提子、先提子后查自杀、自杀非法、占点非法、越界非法、真实棋子分布的单劫和长周期 PSK、停着豁免、非法操作不改变轮次及连续停着数。

RP² 特别夹具：白棋在 (0,0)，黑棋占 (1,0)、(0,1)。其仅剩一气 (18,18)；黑在该点落子后提走白棋。不能误报白仍有一气。

测试夹具可以绕过正常落子设定初始颜色以隔离规则，但必须校验没有预存零气棋串；这些夹具不自动宣称可由空盘合法达到。需要验证可达性的整局测试应通过真实行动序列生成。

### 9.3 计分测试

- 面积分解恒等式；komi 为整数时允许和棋。
- 空盘全部中立；单色边界和混合边界按合同处理。
- 提子不额外加面积分；标死移除与预览恢复正确。
- 跨缝连通的空域不能被平面截图错误拆成两块。
- 双活不自动删除；公共混色空域中立。
- 同一局面的不同显示原点产生同一分数。

拓扑示例：在 19 路环面用黑棋占满一条竖直圈 x=0，用白棋占满另一条 x=9。剩余两个空区域大小为 8*19=152 和 9*19=171，边界颜色均为黑白混合，因此均为中立。在不贴目时两色各有 19 分。这个例子用于验证切口处连通性和非平面式直观，非宣称是稳定最佳对局的终局。

### 9.4 历史与交互测试

双停着 -> 标死 -> 黑确认 -> 修改标死 -> 确认失效；黑白同 revision 确认 -> final；恢复对弈时原死子回来；nextToPlay 与 PSK 历史保留。

悔棋到历史节点后继续不能受到废弃尾部历史影响。含多次停着的悔棋不能删掉更早仍有效的同局面键。JSON 导出导入应重建相同棋盘、轮次、合法着法和结果。认输确认、刷新恢复、复盘只读、幽灵点击同一点均有浏览器测试。

### 9.5 评估测试

势力算法依照实际 neighbors，空盘全零、黑白互换时变号、数值有界、固定输入结果确定。只对真正的图自同构测试等变性，不能假设所有曲面都具有环面那样的平移对称。合法着法提示与规则层一致。

旧 revision 的 Worker 回复必须丢弃；取消分析不影响对弈。未来随机模拟用固定 seed 与固定模拟数测试，不能用固定墙钟时长声称位级可复现。

### 9.6 性能与完整交付

在实际测试机器记录浏览器、CPU、版本与测试命令。目标为普通落子和棋串提示大致在 100ms 内完成，自动保存不明显卡顿；这是验收目标，不是本提案已经测得的结果。势力算法在 Worker 中运行时 UI 保持可操作，支持取消。没有实际运行的测试应标“未运行”，不能伪造绿灯。

## 10. 分阶段实施

### A：拓扑与规则内核

搭建 TypeScript/Vitest 骨架，实现五类图和面、validator、棋串、气、提子、自杀、PSK、pass/history。先跑通参考拓扑表及规则测试，不做 3D，不写占位计分接口冒充完成。

### B：可用的本地双人版

实现 2D 棋盘、轮流落子、幽灵/接缝显示、完整终局协商与面积结算、悔棋复盘、自动保存与 JSON 导入导出。完成后应能从空盘实际下到确定结局。

### C：局势辅助与发布

实现真实拓扑上的势力图、气数警示、一手提子点、参考估值和局限说明；完善 Worker 过期处理和端到端测试，提供 README、Windows 启动脚本及实际测试记录。A+B+C 构成 V1，而不是只有 A 或 B 就声称满足全部需求。

### D：研究与增强

在验收 V1 后，再做有限预算 Monte Carlo/MCTS、3D 同步视图、局域网对战、任意曲面输入或专用训练引擎。保存版本化棋谱、拓扑与确定性种子，为后续研究保留复现实验接口。

工期由实际开发与测试速度决定，不按一次模型回复就应完成来估计。

## 11. 明确禁止的伪实现

不允许按钮只有文字没有逻辑；不允许随机生成胜率；不允许把当前占点直接叫中盘真实终局分差；不允许默认删除所有低气棋串；不允许把两次停着直接等同于无争议终局；不允许图形换成环面但引擎仍按平面算气；不允许把 RP² 四角重复气算两次；不允许普通 KataGo 权重未经环境改造就宣称适用；不允许只保存棋盘而丢失超级劫历史；不允许拿 UI 截图代替规则测试。
